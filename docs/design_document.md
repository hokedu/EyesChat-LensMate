# EyesChat 设计文档

## 1. 项目概述

EyesChat 是一款 AI 视觉对话助手，用户打开摄像头与麦克风后，AI 能够实时看到摄像头画面、听到用户语音，并给出自然流畅的回应。专注于视觉理解准确性、语音交互流畅性和端云协同成本控制。

## 3. 运营成本控制策略

### 思考过的成本控制技巧

#### 已采用的策略

| 策略 | 描述 | 效果估算 |
|------|------|---------|
| 1. 低分辨率帧采样 | 帧尺寸限制在 320×240，detail 设为 "low"，大幅减少 Vision API 的图片 Token | 每帧约 340 tokens（高分辨率需 ~2000+ tokens） |
| 2. 2fps 固定帧率 | 每 600ms 发送一帧，平衡实时性和成本 | 相比 15fps 视频流，减少约 85% 帧数 |
| 3. 会话级 Token 预算 | 默认每会话 50,000 Token 预算，超出即停止 | 防止单个会话成本失控 |
| 4. 轮次限制 | 默认最多 20 轮对话 | 进一步限制最大成本 |
| 5. JPEG 质量 0.6 | 平衡画质和文件大小，不发送原图 | 每帧约 15-25KB 而非 100KB+ |
| 6. 流式响应 | 使用 stream=True，用户无需等待完整响应即可看到文字 | 提升体验同时不额外增加成本 |
| 7. 上下文窗口管理 | 只保留最近 N 轮对话，丢弃最早的历史 | 控制每次请求的输入 Token 数 |
| 8. 端上语音识别 | 使用浏览器 Web Speech API，免费且无需云端调用 | 语音识别零成本 |
| 9. 预估费用仪表盘 | 实时展示 Token 使用和费用估算 | 让用户/开发者可见可控 |

#### 思考过但未采用的策略

| 策略 | 未采用原因 |
|------|-----------|
| 1. 场景变化检测（差异帧上传） | 增加浏览器端计算复杂度，简单场景增益有限；2fps 已足够 |
| 2. 动态 JPEG 质量调节 | 需要客户端网络检测，实现复杂，与帧率调节重叠 |
| 3. 端侧 TensorFlow.js 物体检测 | 增加包体积和加载时间，且对于对话助手的核心场景（回答问题）帮助有限 |
| 4. 画面缓存去重 | 对于摄像头画面这种实时流，去重效果有限 |
| 5. 使用 gpt-4o-mini 做第一轮回答 | 牺牲准确性，对于视觉理解任务影响较大 |
| 6. 批量帧压缩打包发送 | 增加 WebSocket 延迟，不如直接发送最新帧 |

### 成本估算示例

以单次交互为例（用户问 "这是什么水果？" + 一帧画面）：
- 输入 Tokens：~200 (系统提示) + ~50 (用户问题) + ~340 (画面) = ~590 tokens
- 输出 Tokens：~100 tokens
- 总费用（gpt-4o）：(590/1000 × 0.0025) + (100/1000 × 0.01) = $0.0015 + $0.001 = **$0.0025/次**
- 每次对话平均 5 轮：~$0.0125/会话
- 50,000 Token 预算可支持约 **50-70 次交互**

## 4. 技术架构

### 前端（H5 SPA）
- 技术栈：原生 HTML/CSS/JS（单页应用）
- 摄像头：navigator.mediaDevices.getUserMedia
- 语音识别：Web Speech API
- WebSocket：原生 WebSocket
- Canvas：frame capture → JPEG base64

### 后端（FastAPI）
- WebSocket 端点：/ws/chat
- 会话管理：内存 SessionManager（字典存储）
- LLM 服务：OpenAI Python SDK（GPT-4o Vision）
- 流式响应：AsyncGenerator

## 5. 部署与运行

### 启动后端
```bash
cd eyeschat/backend
python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

### 环境变量
配置 `.env` 文件：
```
OPENAI_API_KEY=sk-xxx
OPENAI_BASE_URL=
LLM_MODEL=gpt-4o
```

### 访问前端
直接打开 frontend/index.html 或通过任意静态服务器托管。
